## Structure
- `app/js/domaine/` : logique métier pure, sans DOM, testée. Les signatures réelles du code font foi sur la conception.
  - `savoir.js` : le savoir culinaire (familles de produits, groupes, portion effective, standards maison). Un seul lexique, aucun chiffre : les coefficients viennent des standards de base (`standards-base.js`).
  - `standards-base.js` : les STANDARDS DE BASE (décision du 2026-10-04 « Standards de base et ajustement terrain ») : base métier + repères de portion validés + référentiel culinaire, utilisés directement par les calculs, statut `STANDARD_BASE`, libellé « standard de base » ; la valeur de la propriétaire passe toujours devant (correction du plat > référence du nom > standard maison de la famille puis de la catégorie > standard de base). API (détail en tête du fichier) : `standardDeBase(sujet, usage, { etatPoids, regle })` → `{ usage, valeur, fourchette:{min,max}, unite, uniteSource, etatPoids, sens, origine:'referentiel'|'base_metier', statut, libelle, cible, provenance:{id|table, source, verification, confiance, version}, ecart:null|{referentiel, base_metier}, coefficient? }` ; `rendementDeBase(famille, 'parage'|'cuisson')`, `reperesConservation(famille)`, `reperesCuisson(famille)`, `reperesAide(familleOuTheme)`, `rattachementsDe(usage)`, `texteProvenance(std)`, `USAGES`, `REGLES_GENERALES`. Sujet : clé de famille, `groupe:<clé>`, `categorie:<clé>` ou null. Valeur : milieu de la fourchette (quantités, rendements, temps), borne prudente pour l'hygiène (`sens` du rattachement), seuil seul tel quel ; référentiel quand `verification.resultat === 'confirmee'`, sinon base métier, sinon référentiel ; `ecart` quand les deux diffèrent. Seul ce module importe `donnees/savoir-culinaire.js` (un test le vérifie : ajouter tout nouvel importeur à sa liste).
  - `ajustements.js` + `actions-ajustements.js` : l'ajustement de la propriétaire sur un standard de base (`etat.ajustements`, clé `usage|sujet`, sujet famille / `groupe:` / `regle:`) ; `valeurEffective(etat, sujet, usage)` = sa valeur (origine `propriete`, statut `RESTAURANT_VALIDE`) sinon `standardDeBase` ; branchée dans `calcul.js` pour les étapes parage et cuisson encore à l'état STANDARD_BASE (une correction du plat passe devant). `ajusterStandard` renvoie `{ajustement, avertissement}` (hygiène au-delà de la borne prudente `base.valeur`, jamais de l'autre bord de la fourchette, et au-delà des règles générales qui couvrent la famille : avertit, ne bloque jamais ; sens `plage` = hors de la fourchette, pommes de terre 6–10 °C) ; `controleAjustement(usage, sujet, valeur)` est le contrôle commun à l'action et à l'import (`importer` écarte une entrée dont l'usage n'est pas ajustable, l'unité pas celle du standard ou la valeur hors bornes) ; `revenirAuStandard`. Interface : Réglages > Standards de base (`#/reglages/standards-base`).
  - `analyse-menu.js` + `vocabulaire-plats.js` : lecture des intitulés (`lirePlat`) : éléments au poste, hors poste ou à confirmer selon le menu ; sauce implicite du menu 1 proposée « à confirmer », jamais choisie ; mémoire d'attribution par `nom|menu` (que `lirePlat` consulte : un mot appris n'est plus « à préciser »). Modes de préparation classiques (`MODES` : bonne femme, à la niçoise, lyonnaise, forestière, noms de plusieurs mots seulement) : garniture « à confirmer » avec sa composition possible, jamais décidée. Vocabulaire générique, sans chiffre.
  - `validation.js` + `actions-validation.js` : assistant de validation des portions (une estimation de repère ne devient un standard maison que par la valeur choisie par la propriétaire ; « seulement cette fois » et « plus tard » ne touchent jamais au standard). `actions-achats.js` : liste « à commander » à trois états (suggéré, noté, retiré) ; une ligne fondée sur une valeur INCONNU ne se note qu'avec une quantité tapée ; une ligne calculée sur les standards de base se note sans quantité (noter = confirmer), commandable pour le besoin majoré de la marge (`suiviProduit(...).quantiteCommandable`, `origineQuantite: 'standard_base'`) ; `quantiteAcheter` n'est jamais remplie par le calcul ; une ligne notée sans quantité tapée garde la quantité calculée au moment de la note (`quantiteNotee`), « à relire » si le calcul change ensuite (`raisonARelire`), et `marquerCommande` l'utilise (une ligne INCONNU reste exigeante). `calculerComposant(...).aValider` ne compte plus que les valeurs INCONNU (et la recette non validée) ; `standardBase` dit qu'un standard de base y contribue ; `aMesurer` reste une information. Interface : `ui/feuille-validation.js`.
  - `couverts-midi.js` + `actions-couverts.js` : règle des couverts du midi (décision du 2026-10-07). Un total saisi (`definirCouvertsMidi(etat, date, { total, repartition|null }, h)` écrit `jours[date].couverts = { total, repartition|null, h }` et les prévisions des deux menus ; la prévision porte la certitude « provisoire » dans `portionsMenu`) ; répartition calculée par `repartitionCalculee` = moyenne des 3 derniers jours identiques (`repereVentes`, 3 jours de ventes des deux menus sur les mêmes dates), sinon 1/3 – 2/3 (`PART_MENU_1_SANS_HISTORIQUE`) ; `repartition` non nulle = « décidé par vous » ; `couvertsMidiDuJour` lit les prévisions seules (hors fiches) ; `ventesASaisir(etat, date, heure)` dès `HEURE_VENTES_A_SAISIR` (14:00) ; `apercuCouverts` (sur un clone) donne le « détail du calcul ». `definirPrevision` remet `couverts` à null. `importer` écarte tout `couverts` invalide.
  - `preparation.js` + `actions-preparation.js` : l'écran « Préparer la semaine » (`#/preparer/<lundi>`, `ui/vue-preparer.js`, décision du 2026-10-09), affiché après « Enregistrer la semaine » de l'import. `preparationSemaine(etat, lundi, aujourd)` → `{ jours, aConfirmer, restantInconnu, aFaire, premierJour }` (couverts du midi par jour de menu ; valeurs à confirmer avec standard de base, via `valeursAValider`, ou INCONNU sans chiffre) ; `validerToutAvecStandards(etat, lundi, h)` valide en une action chaque ligne à standard (via `validerStandard`), jamais un INCONNU. Rappel « Préparer la semaine · N à faire » dans les Rappels d'Aujourd'hui.
  - `articles.js` + `actions-articles.js` : l'onglet Articles. `articlesDuPoste(etat, aujourd)` ventile `besoinsProduits` par jour et par menu (du jour à la fin de la semaine, le dimanche = semaine suivante) ; quantité inconnue = `aCompleter`, jamais une alerte ; `cocherArticle` écrit `etat.articlesCoches` (clé « composant|article » → horodatage ; `importer` écarte toute valeur invalide). Pas de stock ni de DLC.
  - `apprentissage.js` + `actions-apprentissage.js` : « l'application en sait de plus en plus sur votre cuisine » (décision du 2026-10-04, point 8). `propositionsApprentissage(etat, aujourdhui)` : 3 corrections de portion du plat dans le même sens (même famille ou catégorie de légumes, même rôle, même état du poids) sur 30 jours (jusqu'à aujourd'hui, jamais une date future), postérieures au dernier standard maison, proposent la médiane arrondie ; un plat compte une fois par jour (menus 1 et 2 confondus), un grammage repris par `reprendreMemoire` (`grammage.repris`) n'est pas une correction, et rien n'est proposé dès que les deux sens sont présents ; la date d'une correction est celle du service du plat. Rien n'est appliqué seul : `accepterApprentissage` passe par `validerStandard`/`corrigerStandard`, `ecarterApprentissage` mémorise `etat.validations['apprentissage:famille|rôle']` (silence 30 jours ou 3 nouvelles corrections). Une ligne de « À confirmer » (`genre: 'apprentissage'`, ouvre `ouvrirProposition` de `ui/feuille-validation.js`).
  - `mise-en-place.js` : lecture de la liste de Production (v109, retours d'essai du 2026-10-09) : `quantiteEnPoids` (« 850 g », « 1,2 kg »), `verbeDe` (table minimale : féculent de base = « Cuire », sinon aucun verbe), `aSaisirPortion` (la portion seule manque : la ligne dit « à saisir », un champ g, `saisirPortionInconnue`). Le glissement entre jours est `jourApresGeste` de `dates.js` (seuil 60 px, dimanche sauté). Production n'a plus aucune liste à dérouler : les résumés (« Déjà prêt », « Pas encore chiffré », lots, charge) sont des lignes tappables qui ouvrent une feuille.
  - `feuille.js` : analyse du texte collé d'une feuille de menus ; `semaineDetectee` (la semaine que décrivent les dates, par vote des jours dont la date est possible) ; `repartirSurSemaine` corrige une date fausse dans la bonne semaine (`corrections`, le plat reste sous son jour) et rend `semaine` ; l'import ouvre le texte à sa place quand au moins 3 jours désignent une autre semaine (`reprendreTexte` de `vue-menus.js`), sans rien enregistrer.
  - `tableau-blanc.js` : données de l'accueil. `aujourdhuiDe(etat, aujourd, heure)` (tableau de bord de la refonte 2) : `menusSurTrois`, `couvertsMidi` (+ `aSaisirVentes`, `ventes`), `aAvancer` (3 lignes, avances que la règle des 2 jours autorise), `avancementJour` (même compte que Production), `ficheProche` (aujourd'hui ou demain), `maintenant`, `decisions`. `bord` = le tableau de bord de la Semaine (menus du jour et des 2 jours suivants, fiches de fonction, « À confirmer » de 3 lignes au plus sans quantité manquante, production et commandes) ; `contexte` (ancienne note) ne s'affiche plus mais désigne la semaine par défaut.
  - `planification.js` : `feuilleDuJour(...).lecture` donne l'ordre de lecture de la feuille Jour (menu 1, menu 2, autres, après service ; une tâche faite aujourd'hui reste dans sa section avec `fait: true`, cochée, grisée sans barré et rangée en bas de son menu dans la vue ; `pretsPlusTard` = faites un jour précédent pour un service à venir, repli « Déjà prêt pour plus tard »). Étapes à avance propre : la règle de préparation (`etat.regles`) peut porter `etapes: [{cle, libelle, avanceMaxJours}]` (la dernière = finition) ; `assurerProductions` crée alors une production `preparatoire` par étape (`etapeCle`, `ordre`), `regleDe(etat, composant, etapeCle)` évalue chaque étape à son propre maximum, `etapesComposant` les liste. Aucune étape ni durée par défaut ; sans étapes, rien ne change. Pâtes et risotto du menu 1 (production principale d'un composant menu 1, féculent, plat_principal) : jour même, jamais proposés en avance (`avancesPossibles`, `lotsPossibles`, « Après service »), sauf `avanceMaxJours` > 0 dans la règle du nom ou production déjà planifiée à la main. `lecture.service1/2` est triée par rôle (base féculent, garnitures féculent puis légumes, composant_recette, herbe, sauce). Conservation : `evaluerAvance(date, service, regle, repere)` ; sans limite saisie (`limiteUtilisationJours`), `repereConservation(composant, etat)` (standard de base, plus courte durée en jours des produits cuits de la famille ; avec `etat`, la valeur ajustée par la propriétaire, la plus précise, passe devant ; `texte` = « se garde N jours », `provenance` courte = « standard de base » ou « votre valeur », sans identifiant technique) remplace « conservation à confirmer » (`conservation: 'referentiel'`, `repere`) et AVERTIT au-delà de sa durée (riz cuit : dès J-2) sans bloquer ni classer « hors règle » ; seule la limite saisie bloque. `evaluationProduction(etat, id, { reelle: true })` et `dateRealiseeProduction` : la conservation (Stock > DLC, « À consommer en priorité ») part de la date RÉELLE du « fait » (une production peut être faite avant son jour prévu) ; `reelNonCompte` dit pourquoi un réel ne couvre pas le besoin (dimanche, hors règle…). `aideRefroidissement()` : phrase de l'aide « Après service » (50 à 10 °C en 2 h au plus). Rattachements en `h`, `semaines`, `mois` : usages `refroidissement`, `limite_duree`, `duree_stockage` (jamais convertis en jours).

## Règles du projet
- Aucune dépendance, aucun build. Ne pas lancer `npm install`.
- Rien sous `app/` n'importe de fichier hors de `app/`. `js/domaine/` reste sans DOM.
- Aucune donnée de restaurant, aucun plat de la carte, aucun grammage d'exemple « maison » dans `app/`. Le vocabulaire culinaire général (formes de pâtes, risotto, rösti…) et le référentiel généré `app/js/donnees/savoir-culinaire.js` sont permis.
- Les jeux de test vivent dans `tests/jeux/`, portent l'étiquette `TEST_ONLY` et ne sont jamais importés par l'application.
- `app/js/donnees/base-metier.js` est généré : ne pas l'éditer à la main.
- Tout nouveau fichier de `app/` doit être ajouté à la liste de cache de `app/sw.js` (un test le vérifie).
- **Toute modification d'un fichier de `app/` impose d'incrémenter ensemble `VERSION` (`app/sw.js`) et `VERSION_APP` (`app/js/version.js`)**, sinon les appareils gardent l'ancienne version en cache.
- Tester dans un navigateur après un changement d'interface : les tests sous faux DOM ne voient ni la mise en page ni IndexedDB.
- **Un parcours se vérifie en le suivant à l'écran, comme le ferait le chef** (ouvrir l'écran, saisir, enregistrer), jamais en injectant les données par un script. Un script ne sert qu'à inspecter.
- Plus aucune validation manuelle : un menu enregistré crée seul ses composants, valides et attribués. Ne jamais réintroduire un bouton « valider ».
- La portion d'un plat se résout au calcul (`grammageEffectif`) : correction du plat, référence du nom, standard maison de la famille, standard maison de la catégorie (clé `groupe:…` dans `etat.standards` ; un légume sans famille en dépend), standard de base (repère validé ou de la base, origine `standard_base`, `repere: 'valide'|'base'`). Elle porte toujours son état de poids ; le calcul part de cet état.
- `BASE_METIER_ESTIMATION` est l'ancien nom de `STANDARD_BASE` (données enregistrées avant le 2026-10-04) : il se lit pareil (`estStandardBase` de `statuts.js`).
- Faux DOM : `querySelector` n'y cherche que par nom de balise. Garder les champs dans une table plutôt que les retrouver par sélecteur. Le code de `app/js/` ne doit jamais lire une propriété propre au faux DOM (`enfants`, `tous`, `declencher` : un test le vérifie) ; un `<dialog>` signale `close` en différé, tester `open` plutôt qu'un drapeau.
- CSS : la classe `.case` est celle des cases à cocher des panneaux ; les cases dessinées du tableau s'appellent `.coche`.
